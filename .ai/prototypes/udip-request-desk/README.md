# UDIP Request Desk (Bydgoszcz City Hall) — interactive backend prototype

This directory contains a static, pre-implementation prototype derived from
`.ai/prototypes/udip-request-desk.requirements.md`. It is a staff-only assistant for Biuro
Komunikacji Społecznej (the AIP) that registers public-information requests, checks the archive
for similar cases, proposes which departments to ask, assembles and anonymises the answer, and
tracks the statutory deadline. The UI is in Polish. Reviewer notes under each screen are in
English.

## Main walkthrough

1 Calendar → 4 Upload & OCR → 5 Request data & deadline → 6 Similar requests → 7 Routing proposal →
8 Department note → 9 Case → 10 Department reply → 11 Draft → 12 Anonymisation → 13 Export & record
sending. Side flows: 2 month view, 14 extension (kwerenda), 15 clarification, 16 error states,
17 supervisor dashboard, 18 archive search, 19 knowledge base, 20 org structure, 21 deadline
settings, 3 empty/no-access states.

The demo date is Monday, 23 November 2026. All people, addresses, contract numbers and figures are
fictional. Department names and symbols are illustrative until the official BIP structure is
imported (requirements Q5).

## What the prototype decides, and what is a proposal you can reject

Decided by the brief (fixed): staff only; manual intake with OCR help; nothing is ever sent (every
outgoing step is "copy/download, then record"); no integrations; every assistant output needs an
officer's acceptance; an offline model in production.

Proposals open for rejection (defaults taken without sign-off, see requirements §4 and §7):

- **D1 / Q1** Deadlines are counted in calendar days with a weekend/holiday shift, per UDIP art. 13
  and KPA art. 57. The brief says "14 working days", which contradicts the statute, so s21 makes
  it a setting.
- **D3 / Q2** A clarification request pauses the clock, and the reply starts a fresh 14 days. BKS's
  current practice of naming a date by hand is available as an override.
- **D4** Similar requests never skip routing on their own.
- **D5 / Q4** The system suggests the next case number but stays editable for SIDAS.
- **D7** Anonymisation covers the letter **and** attachments. Accepted marks are drawn with the
  foreground token: black in the light theme, inverted in the dark theme. Exported files are always
  black.
- The routing deadline for departments is 5 working days before the statutory deadline.
- The model stack in s19 (Bielik 11B, multilingual-e5, Tesseract) is a proposal for the closed
  environment.

## Contradictions and gaps found while drawing

- 14 working days (brief) vs 14 days (UDIP art. 13 ust. 1).
- The 2-month extension limit can land on a weekend (e.g. 23.01.2027), so it shifts too.
- An overdue case can no longer be lawfully extended. The UI offers a reminder or a partial answer
  instead (s16).
- Municipal units (ZDMiKP, Straż Miejska) are separate obligated entities. Whether BKS forwards to
  them or informs the requester is undecided.
- Fees under art. 15, appeals, refusal sign-off (§12) and data retention are not covered yet
  (Q3, Q6, Q7).

## Illustrative only (not implemented)

OCR, similarity search, routing suggestions, draft generation, source checking and anonymisation
detection are all static mock-ups. The only interactions that work are navigation, the redaction
toggle in s12 (click to cycle grey → black → kept), checkboxes, switches and the channel picker.

## Review

Open `index.html` directly, or serve the parent directory on localhost when browser automation
requires HTTP:

```bash
python3 -m http.server 8899 --bind 127.0.0.1
```

Keep the server attached to the current terminal session and stop it immediately after review.

The toolbar supports click-through, presentation and comment modes. Comments are not live
collaboration: they stay in this browser until a reviewer chooses **Export for repository**,
replaces `comments.js` and commits the result. The operation-log format preserves independent
replies and deletion tombstones when reviewers merge exports.

## Limitations

- The HTML illustrates flow and layout; it is not production implementation.
- Sidebar and top bar are generated by a small inline script from one definition, so every screen
  shares the same shell.
- Icons use an embedded SVG sprite instead of `lucide-react`.
- Text is hardcoded instead of translated through `useT()`.
- Sample records must remain synthetic and fictional.
- `tokens.css` is generated. Refresh it with the skill's `sync-tokens.mjs` script rather than editing it.
